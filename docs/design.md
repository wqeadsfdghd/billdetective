# 设计说明

这份文档记录账单侦探在几个关键判断上的取舍。它面向想读代码的人，也面向想贡献规则的人。

## 1. 为什么金额永远是正数

`Transaction.amount` 恒为正，方向由 `Direction` 单独表达（`EXPENSE` / `INCOME` / `NEUTRAL` / `UNKNOWN`）。

把符号和方向混在一个字段里，是记账工具最常见的 bug 来源：一旦某处取反，退款就变成收入、支出就变成负数，总额悄悄失真。分开之后，「这笔钱算不算数」只由 `is_effective` 一个地方决定。

## 2. 三个必须排除的「假支出」

| 类型 | 例子 | 处理 |
|---|---|---|
| 退款 / 关闭 | 交易状态为「退款成功」「交易关闭」「支付失败」 | `is_void_status` 判为无效 |
| 内部转移 | 信用卡还款、转入余额宝、提现、零钱通 | 在 `categorize` 中把方向降级为 `NEUTRAL` |
| 不计收支 | 平台自己标注为「不计收支」的行 | 解析时即归为 `NEUTRAL` |

第二条尤其重要。用信用卡买一杯咖啡，账单里有两条记录：「咖啡 -25 元」和「信用卡还款 -25 元」。如果两条都算支出，实际花费被算成 50 元 —— 用卡越多，误差越大，高到离谱。

## 3. 解析为什么不做硬编码偏移

支付宝导出是 GBK 编码、前面有 4 行说明；微信是 UTF-8-BOM、前面有 16 行说明；两者的列名还随版本变化（`金额` / `金额(元)` / `交易金额`）。

因此解析分三步：

1. **编码轮询** — 依次尝试 `utf-8-sig` → `utf-8` → `gb18030` → `gbk`。`gb18030` 几乎能解码任何字节，所以必须放在最后，否则会掩盖真正的 UTF-8 文件。
2. **表头探测** — 在前 40 行里寻找同时含「时间类」和「金额类」列的那一行，取匹配字段最多者。不写死行号。
3. **列名模糊匹配** — 先精确匹配（归一化后比较，`金额(元)` → `金额`），再做子串匹配，长别名优先，且一列只能被一个字段占用。这样 `交易类型` 不会抢走 `交易时间`。

效果是：即使导出的列顺序变了、多了几列、或者换了银行，也大概率能直接解析。

## 4. 订阅检测的四道过滤

### 4.1 周期拟合

候选周期只有三档：月（30 天）、季（91 天）、年（365 天）。

对每个相邻扣款间隔 `gap`，计算 `k = round(gap / cycle)`。若 `1 ≤ k ≤ 3` 且相对误差 `≤ 25%`，记为该周期匹配成功。**所有**间隔都匹配才算拟合成功。

允许 `k > 1` 是为了容忍漏扣：某个月换了卡付款，间隔变成 60 天，仍应识别为月付而不是判定失败。

误差阈值从最初的 35% 收紧到 25%。35% 时，随机间隔太容易蒙混过关。

### 4.2 金额稳定性

用变异系数（标准差 / 均值）衡量。超过 0.15 直接否决。

订阅会涨价，但不会从 20 元跳到 90 元。而「随机金额的小额消费」必然超过这个阈值。

### 4.3 类别门控

`餐饮美食`、`交通出行`、`日用购物`、`服饰美妆` 四类属于高频习惯消费，默认不参与订阅判定 —— 除非商户名或商品说明里明确含有「会员 / 订阅 / VIP / 包月 / 自动续费」等词。这样「瑞幸咖啡会员」能识别出来，而「第 20 次去瑞幸」不会。

同时设了单商户笔数上限 24：超过这个次数的商户，几乎必然是习惯消费而非订阅。

### 4.4 拒绝周付

周级周期性在账单数据里和「每周固定去同一家店」无法区分。与其报一堆假订阅，不如不报。

### 4.5 最少三次

月付要求至少 3 次扣款。只有 2 个点时，任何两个日期都能凑出某个周期，误报率极高。季付和年付允许 2 次，因为长周期本身已经是很强的约束。

### 4.6 多套餐兜底

一个商户可能同时卖多个套餐（iCloud 50GB 和 2TB）。整组拟合失败且金额差异大时，按整数金额分桶重试，每桶单独判定，且每桶至少 3 次。

## 5. 「隐形」与「固定」的区分

检测到周期性扣款，不等于这笔钱是「隐形」的。

- **隐形订阅**：数字订阅、会员、自动续费 —— 用户容易忘记，是报告的主角。
- **固定账单**：房租、话费、水电、健身房月卡 —— 用户心里有数，但仍然值得知道年化成本。

判定依据是商户与商品说明中的关键词（`会员 / 订阅 / VIP / 连续包月 / 自动续费 / subscription / premium`），而不是消费分类。这样「乐刻健身 月卡续费」会落在固定账单里，不会混进「你被偷偷扣了多少钱」的标题。

## 6. 年化口径

月付 × 12，季付 × 4，年付 × 1。

不用 `365 / 30 = 12.17`。虽然差别只有 1.4%，但用户会拿这个数字去和自己算的账对比，一旦对不上就失去信任。

## 7. 报告为什么是单文件

不引入 matplotlib，图表用内联 SVG 手绘（`report/svg.py` 里约 200 行）。

原因有三：零依赖、断网可用、字体不缺失。副作用是报告天然可以邮件转发 —— 而数据本身始终没有离开用户的机器，这正是这个项目想证明的事：**隐私和好用不是二选一**。

## 8. 已知局限

- 只认 CSV。PDF 和截图导出不支持（OCR 误差会污染全部统计）。
- 现金消费无法覆盖。
- 同一商户的多笔同日消费会被合并为一天一笔（订阅一天不会扣两次）。
- 分类靠关键词，冷门商户会落进「其他」，报告里会明确提示占比。
- 跨年时月度图表的月份标签会重复（如两个「1 月」）。

## 9. 浏览器版与 Python 版的一致性

`docs/index.html` 是一个单文件浏览器实现，用于零安装试用。它**不是另写的一套逻辑**，而是同一套判定规则的第二次实现：

| 环节 | 约束 |
|---|---|
| 编码探测 | 依次尝试 `utf-8` → `gb18030`，用 `fatal` 保证失败即回退 |
| 表头探测 | 前 40 行内找同时含「时间」「金额」的行，取匹配字段最多者 |
| 列名映射 | 精确匹配优先，再做子串匹配，长别名优先，一列只归一个字段 |
| 分类 | 同一份关键词表与优先级顺序 |
| 订阅检测 | 同样的周期候选、25% 间隔容差、CV ≤ 0.15、类别门控、最少 3 次 |
| 年化 | 月付 × 12，季付 × 4，年付 × 1 |

**验收口径**：对 `examples/` 里的两份示例账单，两边必须给出完全相同的数字 —— 500 条记录、491 条有效、总支出 ¥40,466.52、7 项周期性扣款（4 隐形 + 3 固定）。改动任一版检测规则时，都要用这组数字回归验证另一版。

差异只有两处，且都是实现层而非规则层：浏览器版没有终端/JSON 输出，金额以 JS `Number` 计算（展示时四舍五入到分，够用但不像 `Decimal` 那样精确到任意位）。

```bash
# 回归验证（Python 版）
python -m billdetective examples/alipay_demo_2026H2.csv \
                           examples/wechat_demo_2026H2.csv --format text
```

浏览器版的对应验证：打开在线页，把这两个文件一起拖进去，核对上面四个数字。
